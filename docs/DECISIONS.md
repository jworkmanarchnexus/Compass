## Phase 1 decisions (2026-10-11)

- **Tables.** `employees` and `projects` are the Vantagepoint copy (loaded from CSV locally). `users` is Compass's People table (role, name used in drafts, link to a VP employee code). `settings` is effective-dated: saving adds a row and never overwrites, so a run can be reproduced with the settings it was built with. `audit_log` is append-only, enforced by two database triggers (a test proves UPDATE and DELETE are refused). `runs` and `run_warnings` exist but are unused until phase 2.
- **Roles are one pure, tested file** (`shared/rules/roles.js`, fixtures in `shared/rules/tests/fixtures/`). The server calls it on every Admin request; the browser only uses it to hide things. Same pattern as the Toolbox's permission rules.
- **System admin (Kent)**: can read every Admin tab except Commitment patterns, and change nothing. Reason: the handoff says he has no access to PIC content decisions, and the lever behind a commitment is exactly that. My reading, not stated outright.
- **Last-admin guard.** The last active Admin cannot be demoted or deactivated (otherwise nobody could change settings again). Not in the spec; cheap insurance.
- **Assumptions Josh should confirm** (they are settings on Admin → People, so nothing needs rebuilding): Finance sees Turnaround, BD and Pipeline; Marketing director sees BD and Pipeline only (handoff open question 2); PICs see Project Turnaround only, and the BD report and Pipeline watch are off for them (the spec does not say; the handoff open questions do not cover it).
- **Project numbers** in the seed use the mockup's format (`2024-0207`). The real Vantagepoint format is unconfirmed.
- **Admin tabs built:** Project Turnaround settings (the three cards from the mockup), People, Report runs (empty), Audit log. Reminders and standing, BD reports, Pipeline alerts and Commitment patterns show a "arrives in phase N" note.
- **"Active projects as PIC"** in People counts active Vantagepoint projects with that PIC. The mockup column counts Turnaround projects, which need a run; that arrives in phase 2.
- **Header name** `X-Compass-User` for the local sign-in-as, so Compass and the Toolbox never mistake each other's sign-in.

## Phase 2 decisions: the monthly run (2026-10-11)

- **The Vantagepoint pull is a one-method "source"** (`load(period)` returns projects, ledger rows and overhead rates). Locally it reads made-up CSVs (`server/vp-local.js`, `server/db/seed/ledger.csv`, `overhead.csv`). Kent's version runs `reference/handoff/sql/compass_negative_projects.sql` and returns the same three lists. The seed ledger is generated by `tools/make-seed-ledger.js` so the September 2026 run reproduces the mockup exactly: 16 projects, -$450,040, -15.4% of $2.92M billed.
- **Profit math is pure and re-derived from the SQL** (`modules/turnaround/logic/profit.js`), over monthly ledger rows. Money is whole cents. Overhead is applied once per window and rounded to the cent. Projects with no overhead plan or more than one rate are not evaluated and become warnings (the SQL's result set 2), with no fallback rate. **Not tested against real Vantagepoint**: the fixtures are hand-worked, and the real check is to run the SQL for August 2026 and compare to what this code produces from the same rows.
- **Which projects are listed** (`selection.js`) uses three Admin settings: YTD profit below $X, ignore projects billed under $X (my reading: YTD billed), and what to do with no-PIC projects. A no-PIC project is always reported as a warning (result set 3), even when it is also unevaluable.
- **The lock is enforced twice.** `lifecycle.js` gives plain-language refusals; database triggers (`schema.sql`) refuse any change to a published or archived run's rows even if the code had a bug. A published run can only move to archived, with a reason, and nothing else about it may differ. Tests try raw SQL against a published run.
- **Archive-and-rerun** is one step: the old run is archived (reason + the exact word RERUN) and a new draft with the next version number is built from the source with the settings in force then. PICs go on seeing the last published run (possibly an earlier month) until the new one is published; tested.
- **Assumption (mine): a draft can be rebuilt without ceremony.** Only the admin has seen a draft, so "Rebuild draft" re-pulls and re-selects, and is audited. The spec only describes the archive path for published runs.
- **Percentages are not stored** (the data model sketch had pct columns); they are profit / billed, worked out when shown.
- **First appearance** (`first_seen_period`) is the earliest run (any status) a project appeared in. This starts the "plan within 14 days" clock in phase 3. History before go-live is handoff open question 6.
- **The one automatic email** is a text file in `outbox/` locally (git-ignored): count and link only, tested to contain no project or person names. Switch on or off with the Admin setting. How production sends is open question 9.
- **Scheduling.** `npm run run-month` builds the last closed month; with `--scheduled` it does so only on the first business day (weekdays only, holidays are not modelled), so a daily Windows Task Scheduler entry works. It is safe to run twice. Setting it up is Kent's, and nothing here installs a schedule.
- **System admin sees the run list but not run contents** (profit by PIC is performance data, not site operation). Same reading as phase 1.
- **Found while testing:** the shared stylesheet shows the mobile-menu overlay (`.side-scrim`) whenever the window is narrow, which greys out the whole page. Compass overrides it in `shell/shell.css`. **The Toolbox probably has the same problem at narrow widths** (not checked).
- **Review screen is plain on purpose.** Admin > Report runs > Review is a basic table so the lifecycle can be clicked through; phase 3 builds the mockup's Turnaround page (KPI strip, charts, PIC cards) on top of the same data.
