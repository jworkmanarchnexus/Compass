## Phase 1 decisions (2026-10-11)

- **Tables.** `employees` and `projects` are the Vantagepoint copy (loaded from CSV locally). `users` is Compass's People table (role, name used in drafts, link to a VP employee code). `settings` is effective-dated: saving adds a row and never overwrites, so a run can be reproduced with the settings it was built with. `audit_log` is append-only, enforced by two database triggers (a test proves UPDATE and DELETE are refused). `runs` and `run_warnings` exist but are unused until phase 2.
- **Roles are one pure, tested file** (`shared/rules/roles.js`, fixtures in `shared/rules/tests/fixtures/`). The server calls it on every Admin request; the browser only uses it to hide things. Same pattern as the Toolbox's permission rules.
- **System admin (Kent)**: can read every Admin tab except Commitment patterns, and change nothing. Reason: the handoff says he has no access to PIC content decisions, and the lever behind a commitment is exactly that. My reading, not stated outright.
- **Last-admin guard.** The last active Admin cannot be demoted or deactivated (otherwise nobody could change settings again). Not in the spec; cheap insurance.
- **Assumptions Josh should confirm** (they are settings on Admin → People, so nothing needs rebuilding): Finance sees Turnaround, BD and Pipeline; Marketing director sees BD and Pipeline only (handoff open question 2); PICs see Project Turnaround only, and the BD report and Pipeline watch are off for them (the spec does not say; the handoff open questions do not cover it).
- **Project numbers** in the seed use the mockup's format (`2024-0207`). The real Vantagepoint format is unconfirmed.
- **Admin tabs built:** Project Turnaround settings (the three cards from the mockup), People, Report runs (empty), Audit log. Reminders and standing, BD reports, Pipeline alerts and Commitment patterns show a "arrives in phase N" note.
- **"Active projects as PIC"** in People counts active Vantagepoint projects with that PIC. The mockup column counts Turnaround projects, which need a run; that arrives in phase 2.
- **Header name** `X-Compass-User` for the local sign-in-as, so Compass and the Toolbox never mistake each other's sign-in.

## Phase 2 decisions: the monthly run (2026-10-11)

- **The Vantagepoint pull is a one-method "source"** (`load(period)` returns projects, ledger rows and overhead rates). Locally it reads made-up CSVs (`server/vp-local.js`, `server/db/seed/ledger.csv`, `overhead.csv`). Kent's version runs `reference/handoff/sql/compass_negative_projects.sql` and returns the same three lists. The seed ledger is generated by `tools/make-seed-ledger.js` so the September 2026 run reproduces the mockup exactly: 16 projects, -$450,040, -15.4% of $2.92M billed.
- **Profit math is pure and re-derived from the SQL** (`modules/turnaround/logic/profit.js`), over monthly ledger rows. Money is whole cents. Overhead is applied once per window and rounded to the cent. Projects with no overhead plan or more than one rate are not evaluated and become warnings (the SQL's result set 2), with no fallback rate. **Not tested against real Vantagepoint**: the fixtures are hand-worked, and the real check is to run the SQL for August 2026 and compare to what this code produces from the same rows.
- **Which projects are listed** (`selection.js`) uses three Admin settings: YTD profit below $X, ignore projects billed under $X (my reading: YTD billed), and what to do with no-PIC projects. A no-PIC project is always reported as a warning (result set 3), even when it is also unevaluable.
- **The lock is enforced twice.** `lifecycle.js` gives plain-language refusals; database triggers (`schema.sql`) refuse any change to a published or archived run's rows even if the code had a bug. A published run can only move to archived, with a reason, and nothing else about it may differ. Tests try raw SQL against a published run.
- **Archive-and-rerun** is one step: the old run is archived (reason + the exact word RERUN) and a new draft with the next version number is built from the source with the settings in force then. PICs go on seeing the last published run (possibly an earlier month) until the new one is published; tested.
- **Assumption (mine): a draft can be rebuilt without ceremony.** Only the admin has seen a draft, so "Rebuild draft" re-pulls and re-selects, and is audited. The spec only describes the archive path for published runs.
- **Percentages are not stored** (the data model sketch had pct columns); they are profit / billed, worked out when shown.
- **First appearance** (`first_seen_period`) is the earliest run (any status) a project appeared in. This starts the "plan within 14 days" clock in phase 3. History before go-live is handoff open question 6.
- **The one automatic email** is a text file in `outbox/` locally (git-ignored): count and link only, tested to contain no project or person names. Switch on or off with the Admin setting. How production sends is open question 9.
- **Scheduling.** `npm run run-month` builds the last closed month; with `--scheduled` it does so only on the first business day (weekdays only, holidays are not modelled), so a daily Windows Task Scheduler entry works. It is safe to run twice. Setting it up is Kent's, and nothing here installs a schedule.
- **System admin sees the run list but not run contents** (profit by PIC is performance data, not site operation). Same reading as phase 1.
- **Found while testing:** the shared stylesheet shows the mobile-menu overlay (`.side-scrim`) whenever the window is narrow, which greys out the whole page. Compass overrides it in `shell/shell.css`. **The Toolbox probably has the same problem at narrow widths** (not checked).
- **Review screen is plain on purpose.** Admin > Report runs > Review is a basic table so the lifecycle can be clicked through; phase 3 builds the mockup's Turnaround page (KPI strip, charts, PIC cards) on top of the same data.

## Phase 3 decisions: Project Turnaround (2026-10-11)

**The plan log**
- **Append-only, twice over.** There is no API path that edits or deletes an entry, and database triggers refuse any `UPDATE` or `DELETE` on `plan_entries` (a test tries both). A mistake is a Correction entry pointing at the original, which shows "Corrected Jul 21".
- **Commitments are not their own table.** Whether one is open, done, missed or moved is worked out by replaying the log (`modules/turnaround/logic/plan.js`), so nothing mutable can drift from the history. This replaces the `commitments` and `commitment_events` tables in the handoff's data-model sketch. Entry kinds are explanation, commitment, update, correction, done, date_revised, missed (written by the system) and admin_note.
- **Entries belong to the project, not the run**; the plan cycle is the calendar year (YTD only, fresh start in January, last year stays readable).
- **A closed commitment is final.** Done after its date is "not kept" (shown as Done late); a Missed one cannot be reopened. Moving a date needs a reason and keeps every earlier date.
- **The lever, the number and the actual result never reach a PIC**, not even the author after posting. The server strips them (tested against every PIC, Finance and the plan page). Consequence: the Mark done form cannot say "dollars" or "hours", so it asks for the result "in the same unit as your estimate".
- **Admin may only add labeled notes**, which never count toward a PIC's record. Only the project's own PIC writes plan content; Finance, Marketing and the system admin cannot.

**Rules I had to choose** (the mockup's own rows disagree with each other, so I wrote one consistent rule and made every number a setting; **please confirm or change**):
1. **Update due date** = the earlier of (last PIC entry + 30 days) and the next open commitment's date. Status: Overdue past that date; Update due within 14 days (`due.soonDays`); otherwise Current. Current also needs an open commitment. No commitment yet this year = No plan (an explanation alone does not count); its due date is 14 days after the project first appeared on a published run, never before Feb 1.
2. **Missed**: the daily job records a commitment as Missed 14 days after its date (`due.missedAfterDays`). The mockup shows one marked Missed after 2 days and others still "past due" after 11, so there is no rule to copy.
3. **On time**: an entry is on time if made by its due date: the first by the first-plan date, each later one within 30 days of the one before. Kept = Done on or before its (current) date.
4. **Standing** needs a minimum of 3 items behind a measure (`standing.minSample`, my addition). Without it, one missed commitment made a PIC "Escalated". With fewer than 3 on a measure it is left out of the label.
5. **Drafts are one per PIC per situation** ("overdue", "no plan"), listing that PIC's projects, taking "one per PIC" literally. The mockup shows one project per card because each PIC had one. Reminder 1 at +3 days (casual), reminder 2 at +10 (direct, only if reminder 1 was sent), escalate at +21 (listed as a conversation, no draft). A dismissed draft never returns for that item; a waiting draft is withdrawn if the PIC fixes it. A PIC who wrote in the last 2 days, or was sent a reminder in the last 5, is skipped that day.
6. **Not built from the ladder:** "Repeat next monthly run" (needs the monthly summary, which does not exist yet).
7. The mockup's no-plan drafts appear 6 days after a project joins the list; the ladder counts from the due date (14 days), so they would start at 17. Shorten `due.newProjectDays` to see them sooner.

**Screens and data**
- **One page for everyone.** The server builds the Turnaround page and removes what the viewer may not see (`visibility.picRecords` hides on-time/kept/standing; each PIC always sees their own). The admin reviews a draft run on the same page before publishing. "Just mine / Everyone" is shown to PICs only.
- **Charts come from the run.** Each run stores 12 months of firm-wide month-end figures and each listed project's YTD profit by month (`run_history`, `run_project_history`), locked with the run, so no page ever asks Vantagepoint. Kent's pull must be able to produce past month-ends (the SQL run once per month, as the Excel report does).
- **Not built yet:** Export Excel; "Contract fee" and "Billed to date" on the plan page (the validated SQL does not pull fees); market sector on the plan page; Home's "Needs your attention" (phase 4).
- **Daily job** (`npm run daily`): records Missed, prepares and withdraws drafts, and emails the admin a count and a link on weekdays, once a day. Nothing is scheduled; Kent does that.
- **`COMPASS_TODAY=2026-10-07`** pins the date. The demo's plan logs are written around the mockup's day; on any other day the statuses shift (days overdue grow) and the daily job may record more Missed. In PowerShell: `$env:COMPASS_TODAY='2026-10-07'; npm.cmd start`.
- **The demo seed** now has two published runs (August and September) and made-up plan logs, and runs the daily job once on the demo day. September 2026 reproduces the mockup's numbers: 16 projects, -$450,040, 8 of 16 plans current, 4 waiting, 2 new since August. Differences: "3 off" is 0 (no seed project leaves the list), and all 14 continuing projects "got worse" (year-to-date losses only deepen as months pass). The mockup shows 7 and 7.
- **Fixed from phase 2:** `npm run seed` would have failed once a run was published (the lock triggers blocked the reset). A reset now drops the guard triggers, clears the tables and recreates them. Tested.
- **Found while testing:** the shell's native `append()` prints a `null` child as the word "null". Fixed on the plan page and the run page (archived runs had it).

## Phase 4 decisions: Home (2026-10-11)

- **Home shows only what exists.** The mockup's pipeline alerts, the BD report, the weekly snapshot, "$ unassigned to a market" and the Firm snapshot tiles have no data source yet (BD and Pipeline are phase 5+; utilization and net profit are handoff open question 5). They are left out rather than faked. When a source exists, each is one more item in `server/home.js`.
- **By role** (`server/home.js`, tested): Admin gets Needs your attention, Recently published, Data checks and Next scheduled runs. System admin gets Data checks and Next runs only (it keeps the site running and does not see run contents). A PIC gets **Your projects** (their own plan status with a link to add to the log) and Recently published. Finance, and Marketing if allowed, get Recently published. Your projects for PICs is my addition; the spec only defines Needs your attention for the Admin.
- **Needs your attention** (Admin): a draft run waiting for review (hidden if the existing setting "Show it in Needs your attention on Home" is off), check-in drafts waiting, and projects 21 or more days past due (a conversation, not a draft; the same list as the check-in page).
- **Data checks:** the monthly pull (is last month's run built?), active projects with no PIC, active projects whose PIC has no Compass login (they cannot write a plan or get a reminder), projects a run could not evaluate, and whether the daily checks ran in the last 2 days. "Vantagepoint pull status" is judged from the run, since a real pull log does not exist yet. Daily checks show "have not run yet" on a fresh demo because the seed's own first run is not logged; that is accurate and goes green after the first real run.
- **Next scheduled runs** shows the monthly run (next first business day) and the daily checks. The weekly snapshot and the BD run will be added with their modules.
- Weekends and holidays: "first business day" is still the first weekday (holidays are not modelled).
